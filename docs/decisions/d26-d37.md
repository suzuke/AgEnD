## D33

- 決定：
  1. 一個 agent 同時最多持有一個 task，從派工起持有到 done 或取消，包括等待 submit、checks、review 的期間。審查指派就是 reviewer 的那一個 task。取代可設定的每個 instance task concurrency。
  2. 要求修改後的返工一定回到 task 目前的 task 持有者。它仍持有這個 task，所以不會有「task 持有者正在忙別的 task」的情況，返工不需要等它空出來。
  3. 持有者無法繼續時：額度用盡 → 依 D18 改派同角色、另一個允許 backend 的成員，並交接審查意見與目前的 branch；沒有空的成員就在角色人數上限內開臨時 instance；都不行就排隊（原因：額度）。持有者被操作者刪除 → 立即改派同角色成員（或在人數上限內開臨時 instance）。臨時 instance 只在它持有的 task 結束後才回收，所以返工中的作者不會被回收。
  4. 取消「等待 fanout 的父 task 不佔名額」的特例：父 task 的 agent 等待期間照樣持有 epic；子 task 派給其他 agent；team 內互等由既有的互等偵測發現，並通知使用者。
- 理由：一個 agent 一個 task、task 持有者在審查期間仍持有 task，返工就不會遇到它在忙；剩下的失敗情況只有額度用盡與被刪除。shim 一次只能把一個 agent 導向一個 worktree，一個 agent 同時做兩個 branch task 在結構上本來就做不到。
- 接受的代價：agent 在等 checks／review 時閒置；並行度等於 agent 數，靠角色人數上限（臨時 instance）調整。
- 否決的方案：草稿原本的行為——每個 instance 可設定 task 數、返工遇到 task 持有者沒空位就排隊等它、它不在就排隊不改派、等待 fanout 的父 task 不佔名額（見 [gate-01-core.md 的 Q1](../gates/gate-01-core.md#q1返工時-task-持有者不能接round-1-review-i8)）。
- 證據：使用者 2026-09-25 決定（第 1 施工關 round-1 review I8 的待決定事項）。實作與測試：`crates/agend-core/src/policy/assign.rs`。

## D34–D37 的共同背景

使用者拿 AgEnD 對照「AI monotasking vs multitasking」的最佳實踐圖：多個功能平行進行，**人是瓶頸**；計畫在實作前先審；用對話設定脈絡；把人切換脈絡的成本壓到最低。D34–D37 各處理其中一點。

## D34

- 決定：新增內建 workflow `planned`：`work`（planner，產出計畫結果）→ `approval(by = "human", bind_head = false)` → `work`（dev，產出 branch）→ `submit` → `command` → `approval`（reviewer 角色，`bind_head = true`）→ `merge`。
- 理由：人的注意力是瓶頸；人審在計畫階段槓桿最大（最便宜修正）；實作的審查交給 agent reviewer 與 checks。
- 否決的方案：人審每個實作 diff（人變成瓶頸）；完全不讓人看計畫（方向錯到實作完才發現）。
- 證據：使用者 2026-09-25 決定。實作：`Workflow::builtin_planned`；存檔格式鎖在 `xtask/tests/golden/workflow-planned.toml`。

## D35

- 決定：needs-you（請示）是對話：agent 提問時可附選項，人可以選選項或用自由文字回答；thread 可多輪（提問、回答、追問、結論）；回答可以來自 TUI 或 Telegram（或 CLI）。client protocol v1 以 additive 方式擴充（`Ask.options`、`AskFollowUp`、`AskResolve`、`AnswerAsk`、`AskCreated`、`AskUpdated`、`AttentionRequired.ask`），版本仍是 1.0。
- 理由：只有選項的問題常常問不準；用對話設定脈絡，比來回開新問題省人的時間。
- 否決的方案：只支援選擇題；另開 protocol major。
- 證據：使用者 2026-09-25 決定。實作：`protocol::ask`；golden JSON 測試在 `xtask/tests/protocol_compat.rs`（含舊格式仍可解碼）。

## D36

- 決定：needs-you 的排序是 core 純函式 `policy::attention::order`：先看解決後能讓多少 task／agent 繼續（多的在前），再看等待時間（最久的在前），最後以 id 決定順序。
- 理由：人的注意力是最稀缺的資源，先處理能放行最多工作的項目；規則是純函式才能窮舉測試（同 D25）。
- 否決的方案：只照時間排序（重要的項目被淹沒）；在 UI 裡各自排序（TUI 與 Telegram 不一致）。
- 證據：使用者 2026-09-25 決定。實作與測試：`crates/agend-core/src/policy/attention.rs`。

## D37

- 決定：needs-you 項目附 context recap：功能目標、目前為止的決定、在問什麼、之後會發生什麼。core 只定義資料型別（`protocol::ask::ContextRecap`，放在 `AttentionRequired.recap`）；內容由 daemon 產生（第 11 施工關）。
- 理由：人切換到一個請示時最貴的是重建脈絡；recap 讓 UI 在切換時直接顯示。
- 否決的方案：讓人自己去翻 task 歷史。
- 證據：使用者 2026-09-25 決定。
