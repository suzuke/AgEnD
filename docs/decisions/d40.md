## 收件與恢復的邊界

`agend_ack` 已在 [bridge 基礎](../gates/gate-12a-bridge.md) 實作；完整 Claude 啟動配置及 Driver 接入仍在施工，尚未完成驗收。工具報告的是 Claude 主動確認收件；模型可能漏呼叫，這時只能保留未確認。channel 寫成功沒有 backend ACK，UserPromptSubmit 在模型處理前觸發，普通 Stop、背景事件或 `stop_hook_active: true` 不能替指定訊息確認。

訊息 id 仍是既有 `messages` 的唯一冪等身分。投遞識別碼只是這則訊息某次投遞的關聯資料，不另建一套訊息去重；同 id 同內容重送命令回目前狀態，同 id 不同內容拒絕。ACK 補送也不得重新派一輪工作。

core 的 DeliveryState 四個值與轉換不因「結果不明」新增一個值。缺寫出結果時 DB 可能仍是 queued，但必須另存投遞已開始／結果不明的 metadata，顯示此原因並禁止一般 queued 重送路徑；不能解讀為「可確定尚未送出」。有效 ACK 到達時可依已保存的投遞關聯，先補 sent 再 confirmed，遵守既有 forward transitions。

P7 的 14 天事件紀錄不是恢復唯一來源。未終結訊息、投遞關聯與未同步 ACK 必須保留足以核對的資料，不能先刪事件或訊息再宣稱冪等成立；實作須補 14／30 天邊界、延遲 ACK 與人工終結回歸。這個例外只擴充本次 Claude 接入，不由文件改動宣稱既有 Codex retention 已變。
