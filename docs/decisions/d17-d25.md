# 決策 D17–D25

> **TL;DR**
> - CLI 分工、角色分派、workflow 格式與版本、施工順序、文件規則、安裝施工關、分派規則的位置。
> - 記住：人工核准 merge 只有一種寫法：`approval(by = "human")`。
> - 下一步：回 [../DECISIONS.md](../DECISIONS.md) 找其他決策。

每條格式：決定 · 理由 · 否決的方案 · 證據。

「規劃 §x」指設計階段計畫 [REWRITE-PLAN.md](../research/REWRITE-PLAN.md)；其他證據檔在 [../research/](../research/README.md)。

## D17

- 決定：CLI 分 agent 命令與操作者命令。agent 命令共 11 個：`status`、`done`、`result`、`review approve`、`review changes`、`send`、`inbox`、`ask`、`block`／`unblock`（一個命令、兩個動詞）、`task create`、`remind`。daemon 依呼叫者身分限制權限，拒絕時附正確命令。
- 理由：命令總數 < 15、常用命令參數 ≤ 2（規劃 §4.7）；agent 只傳意圖，其餘由 daemon 推得。
- 否決的方案：未另外記錄（使用者在設計討論中決定）；v1 對照是 34 個 MCP tool（[inventory.md §3](../research/inventory.md)）。
- 證據：v1 使用量（10 天）：inbox 18,937、task 12,193（其中 `task get` 4,460；規劃 §3.1 另一次統計為 12,196，兩次取樣時間不同）、send 9,679（[usage.md §2](../research/usage.md)、規劃 §3.1）。

## D18

- 決定：agent 不建立 instance。`agend task create --role <角色>`，daemon 依 team 的角色範本分派或開臨時 instance。角色範本 = 允許的 backend、模型等級、指示、人數上限（min／max）、session 策略。
- 分派規則：審查排除作者並優先不同 backend；退回修改回原作者；超過上限排隊；等待 fanout 的父 task 不佔名額；偵測 team 內互等並通知；需要不存在的角色時轉成 ask；額度用盡改派其他允許的 backend。
- 理由：使用者在設計討論中決定；跨廠牌互審與額度轉派是差異化第 2 點。
- 否決的方案：agent 自己開 instance（明文「沒有這個退路」）。
- 證據：v1 同一題派給兩個 agent 比較後選一個、48 個 task 被改派兩次以上（[workflow-validation.md §5](../research/workflow-validation.md)、§7）。

## D19

- 決定：workflow 定義格式為 TOML；DB 為真相來源，編輯時匯出／存回，每次存檔為新版本。存檔檢查：id 唯一、kind 合法、submit 前需有產出 branch 的 work、有 submit／merge 必須 `requires = ["repo"]`、merge 前需有 `bind_head` 的 approval（否則明寫 `allow_unreviewed = true`）、`on_fail` 只能指向前面的關卡、角色須存在於套用的 team。命令：`agend workflow list/show/new --from/edit/apply/check/history/rollback/delete`、`agend team set-workflow`；內建 workflow 唯讀。
- 理由：新增組合或調參數不需改程式碼（規劃 §4.5.0）；TOML 與 `config.toml` 一致，人和 agent 都讀得懂；DB 仍是唯一真相來源（不會有 v1 fleet.yaml 那種回寫問題）；存檔檢查把靜默的設定錯誤變成附修正方法的錯誤。
- 否決的方案：YAML；TUI 裡的 workflow 編輯器（範圍）；外掛系統（相容性、沙箱、除錯成本——v1 式的複雜度）。
- 證據：關卡模型以 v1 8,347 個 task 驗證：原 5 種關卡完全符合 76%、需要新參數 16%、需要新型別 8%；缺口由 `fanout`、task 關係與操作、共用 `timeout` 補上（[workflow-validation.md](../research/workflow-validation.md)）。

## D20

- 決定：取消「每個 repo 選自動或人工 merge」的設定；需要人工核准就在 workflow 裡於 merge 前加 `approval(by = "human")`。
- 理由：一種機制取代兩種——人工門檻就只是一個 `approval(by="human")` 關卡。
- 否決的方案：另設 per-repo 的自動／人工 merge 政策（規劃 §4.5）。
- 證據：規劃 §7 風險：業界主流（WorkOS、Factory.ai、Cursor）反對 agent 自動 merge，所以必須能選人工核准（[competitors.md](../research/competitors.md)）。

## D21

- 決定：task 建立時記下 workflow 版本並固定；修改 workflow 只影響之後新開的 task；進行中的 task 照原版本走完。
- 理由：固定版本就不必把進行中的 task 從舊關卡對應到新關卡（遷移複雜度的來源）。
- 否決的方案：一律用最新版本；把進行中的 task 對應轉換到新版本的關卡（明文「不做」）。
- 證據：規劃 §2 D21。

## D22

- 決定：施工依 crate 由下往上分 12 個施工關（core → testkit → shim → holder → store → daemon↔holder → codex driver + delivery → client + server → CLI → pipeline／git／forge local／supervisor → TUI → 其餘 adapter）。每個施工關單獨驗收（`cargo test -p`、clippy、check-deps、`cargo xtask accept <施工關>`、文件更新、verifier），使用者確認後才開下一個施工關；需要改 core 時先改 core 並重過第 1 施工關。
- 後續：D24 加上第 13 施工關「安裝與發布」；規劃 §2 D22 原文仍寫 12 個施工關。
- 理由：每個施工關可獨立驗證（D9）。
- 否決的方案：規劃 §6 的功能階段 1–5（改成里程碑）。
- 證據：規劃 §2 D22。細節見 [../ROADMAP.md](../ROADMAP.md)。

## D23

- 決定：文件以繁體中文為主、程式輸出以英文為主；每個 crate 有 README.md 與 TESTING.md；AGENTS.md 為所有 agent 的唯一入口（不建 CLAUDE.md）；文件以 ADHD 讀者為預設（TL;DR、先結論、表格與清單、固定章節、下一步）。
- 理由：使用者的要求；v1 為維護雙語文件付出很大成本（甚至有專門檢查雙語一致的 invariant 測試），所以只用一個主要語言；只有 AGENTS.md 一個入口，避免各工具專用的入口檔彼此漂移。
- 否決的方案：英文為主的文件；另設 CLAUDE.md。
- 證據：規劃 §2 D23。

## D24

- 決定：新增第 13 施工關「安裝與發布」：服務註冊、`agend uninstall`、`agend telegram setup`（由 daemon 配對）、`xtask release`、brew、GitHub release、`cargo install`。驗收：CI 以全新 HOME + 假 agent 從安裝到第一個 task 完成 < 5 分鐘；每項 doctor 檢查都有「故意弄壞 → 看到修正指令」的測試。第 9 施工關只做 `doctor` 與 `init`。安裝規則（版本範圍、登入偵測、git 最低版本、服務設定檔文字）放 agend-core 的 `setup` 純函式模組，由 `agend` 的 `setup` 模組執行。
- 理由：使用者在設計討論中決定；安裝需要其他全部元件，放最後一個施工關。
- 否決的方案：未另外記錄（使用者在設計討論中決定）。
- 證據：[REWRITE-PLAN.md](../research/REWRITE-PLAN.md) §2 D24；細節見 [../ROADMAP.md](../ROADMAP.md)。

## D25

- 決定：D18 的分派規則是純邏輯，放在 agend-core `policy::assign`；daemon 只提供候選成員與負載等輸入。
- 理由：純規則可以窮舉測試；daemon 只負責提供輸入。
- 否決的方案：未另外記錄（使用者在設計討論中決定）。
- 證據：使用者在設計討論中確認。
