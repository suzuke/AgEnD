# 決策 D1–D8

> **TL;DR**
> - 程序模型、holder、forge、shim、CLI、DB 的基本決定。
> - 記住：「使用者在設計討論中決定」表示沒有另外的書面理由；不要自行補。
> - 下一步：回 [../DECISIONS.md](../DECISIONS.md) 找其他決策。

每條格式：決定 · 理由 · 否決的方案 · 證據。

「規劃 §x」指設計階段計畫 [REWRITE-PLAN.md](../research/REWRITE-PLAN.md)；其他證據檔在 [../research/](../research/README.md)。

## D1

- 決定：daemon 對外只有一套公開、有版本的 protocol（事件串流 + 終端串流）。TUI 是第一個 client，GUI 之後接上（需要時加 WebSocket）。
- 理由：GUI 與 TUI 共用同一協定；外部 GUI 用 core 產生的 JSON schema（D11）。
- 否決的方案：未另外記錄（使用者在設計討論中決定）。
- 證據：規劃 §2、§4.1。v1 對外面有 34 個 MCP tool、JSON 控制 API、TUI bridge 等多個介面（[inventory.md §1](../research/inventory.md)、§3）。

## D2

- 決定：daemon 常駐（launchd／systemd），可從 TUI restart／shutdown；重啟前預檢新 binary，失敗就不切換。
- 理由：使用者在設計討論中決定；相關證據是 v1 的 daemon 會跟著終端死、且 app 與 daemon 誰擁有誰的框架反覆失敗。
- 否決的方案：v1 的「app 永遠 attach + 自動 spawn detached daemon」（#881、#882、#903 三次被 revert，#906 換手法才成功）。
- 證據：#3499（關終端 daemon 跟著死，規劃 §4.9）；[history.md §3](../research/history.md) 案例 3。

## D3

- 決定：daemon 重啟時 agent 不斷線。runtime 採自有 holder（portable-pty + alacritty_terminal，取自 v1 零件），每個 instance 一個，持有 PTY、畫面狀態與附屬程序。保留一層薄 `Runtime` 介面。
- 理由：使用者在設計討論中決定（推翻 spike 建議，沒有另外的書面理由）。spike 列出的相關事實：三種方案硬殺上限相同；自有 holder 零外部依賴（R9）；v1 已有 portable-pty 與 VTerm「重連時送乾淨畫面」的做法可重用。
- 否決的方案：tmux、herdr（runtime spike 的建議是 herdr）；以 ring buffer 重播重建畫面（可能從轉義序列中段開始）。
- 證據：[runtime-spike.md](../research/runtime-spike.md)；v1 關機會殺掉所有 agent（`src/daemon/mod.rs:1609-1660`）；v1 hot-restart 是等前任退出才 spawn（規劃 §8 r1）。
- 已知上限：holder 自己被硬殺，裡面的 agent 一起死。

## D4

- 決定（最新版）：流水線的提交與 merge 透過 Forge（第一版 local、github）；驗證是 `command` 關卡。
- 理由：workflow 是關卡組合，新增組合或調參數不需改程式碼（規劃 §4.5.0）；checks 因此只是一種關卡。
- 否決的方案：規劃原版 D4 的「Forge + Checks（指令、forge CI）兩個介面，每 repo 各自設定」，被 D19／D20 取代。
- 證據：規劃 §2 D4 原文與 architecture 頁 D4 的差異。
- 未決：forge CI（GitHub checks）結果如何進流水線，來源沒有新說法。

## D5

- 決定：git shim 是一級元件，放在 v2 repo 內做成獨立 crate（`agend-shim`），隨同一個 binary 發布，以 argv[0] 分派。
- 理由：git 防護內建於 orchestrator 是差異化第 5 點；調查的 17 個同類工具都沒內建，只有獨立小工具。
- 否決的方案：v1 的外部 vendored agentic-git（`vendor/agentic-git` 帶著與主程式不同步的檔案副本）。
- 證據：[competitors.md](../research/competitors.md)「沒人做好」第 2 點；[inventory.md §4](../research/inventory.md) 第 11 點。

## D6

- 決定：不用 HMAC。binding 存 DB，daemon 為每個 agent 寫出唯讀快照檔給 shim。
- 理由：唯讀快照和 HMAC 一樣只是安全帶，同 uid 的 agent 都能繞過（規劃 §4.6），所以不值得保留 HMAC 的機制。
- 否決的方案：v1 的 HMAC 簽章 binding（`verify_sidecar`、`ensure_key`、`sign_binding`、`integrity_core`）。
- 證據：規劃 §4.6；v1 自己的威脅模型註解說 HMAC「不是多使用者安全邊界」（[inventory.md §5](../research/inventory.md)）。

## D7

- 決定：agent 介面以 CLI 為主；handler 與傳輸分離；需要時由同一份定義產生 MCP 轉接層。
- 理由：CLI 啟動 p50 4.1 ms、unix socket 來回 0.014 ms（規劃 §4.7 實測）；同一份定義避免 schema 與 handler 漂移。
- 否決的方案：v1 的 MCP 優先（34 個 tool）。
- 證據：v1 `mcp_retired_arg_keys_invariant.rs`（參數改名後 handler 讀舊名拿到 null）。

## D8

- 決定：instance 全部存 DB（不再有 fleet.yaml），透過 CLI／TUI 建立與修改；常駐或臨時是 DB 裡的 `lifetime` 屬性。備份靠 `agend export`／`import` 與每日 `VACUUM INTO`。
- 理由：唯一真相來源；daemon 不用回寫人寫的 YAML。
- 否決的方案：v1 的 fleet.yaml。
- 證據：規劃 §4.8。注意：規劃 §8 r1 更正過，「fleet.yaml 註解被清」已由 `fee2430e` 修復，不能再當理由。
