## D9

- 決定：每個模組都能獨立驗證與測試（規劃 §5.1）：依賴單向、外部邊界有 trait + 假實作、契約測試、輸入用 producer 產生、每個模組可單獨跑起來。
- 理由：避免假綠測試；讓人與 agent 都能驗證單一模組。
- 否決的方案：來源未記錄。
- 證據：v1 #1483（matcher 比對的格式 production 從不送出，測試全綠但是死碼）、#1493 規則；v1 有 48 個 invariant／guard 測試在補架構該保證的事（[history.md §5](../research/history.md)）。

## D10

- 決定：crate 劃分四條準則——(1) 編譯器強制的限制；(2) 獨立程序、有自己的穩定性要求；(3) 對外使用；(4) 多 crate 共用的測試基礎設施。其餘為模組 + trait。新增 `agend-client`、`agend-testkit`（dev-only）、`xtask`。
- 理由：「其餘為模組 + trait」——沒有符合準則的約束就不切 crate。
- 否決的方案：來源未記錄。
- 證據：規劃 §5、architecture 頁 crate 圖。

## D11

- 決定：protocol 放 core（外部 GUI 用產生的 JSON schema）；agend-client 同步 I/O；driver／forge／store 為 daemon 內模組 + trait；holder 與 daemon 同一 binary、每個 instance 一個 holder；流水線狀態機（6 種關卡 + task 關係與操作）放 core 為純函式。
- 理由：CLI 與 shim 的啟動路徑不建 runtime（規劃 §4.7）；狀態機純函式可單元測試與 property test。
- 否決的方案：來源未記錄。
- 證據：規劃 §4.7、§5.1 表格。

## D12

- 決定：每個 instance 同時只屬於一個 team。內建不可刪除的預設 team `general`；沒指定 team 的 instance 與 task 都歸它，不存在「沒有 team」的特例；`general` 也有共享目錄。
- 理由：消除特例。
- 否決的方案：「沒有 team」的 instance（被明確排除）。
- 證據：規劃 §2 D12。

## D13

- 決定：`teams/<team>/` 放 team 說明（注入給成員）、共享筆記、共享產出；成員各自的 workspace 不放進去。Telegram：一個「需要你」topic + 每個 team 一個 topic；個別 instance topic 可選、非預設。
- 理由：來源未逐字記錄；對應差異化第 4 點「人只處理例外」。
- 否決的方案：個別 instance topic 為預設（改為可選）。
- 證據：規劃 §1、§2 D13。

## D14

- 決定：main 前進後自動 rebase 並重跑 checks；rebase 無衝突且 branch 自身 diff 的 `git patch-id` 不變則保留核准，否則退回 work。
- 理由：來源未逐字記錄；它回答了規劃 §4.5 原本待定的兩個問題（checks 是否重跑、既有核准是否失效）。
- 否決的方案：來源未記錄。
- 證據：規劃 §4.5（待定條目）→ §2 D14。

## D15

- 決定：team 有 0 或 1 個 repo。workflow 宣告需求（`code` 需要 repo；`research` 不需要）；無 repo 的 team 沒有 worktree 與 shim；`general` 無 repo。跨 repo 工作用跨 team 的 `depends_on`。
- 理由：來源未記錄。
- 否決的方案：一個 team 多個 repo（來源未明寫否決理由）。
- 證據：v1 真實 task 有跨 repo 依賴只能寫在描述裡（[workflow-validation.md §5](../research/workflow-validation.md)，`t-20260719142708627000-80319-34`）。

## D16

- 決定：claude driver 採互動式 TUI + hooks。狀態看 hooks；排隊用 Stop hook `decision: block`（先取出佇列再回傳，`stop_hook_active` 防迴圈）；閒置時經 channel 送；中斷 = `Esc` 後立即經 channel 送（Esc 不觸發 Stop，不做等待）。專案 CLAUDE.md 必須說明 agend channel 訊息來自使用者自己的團隊；訊息內可另加 from／task／request 標頭。
- 理由：channel 在忙碌時送到的訊息可能不被處理；Stop hook 可可靠地注入一次後續 turn。
- 否決的方案：忙碌時直接經 channel 送（C1：訊息被擱置）；Esc 後等 Stop 再送（F3：Esc 後不會有 Stop）；`-p` stream-json 的 `control_request interrupt`（只在 headless 模式驗證過，互動模式未驗證）。
- 證據：[spike-claude.md](../research/spike-claude.md) C1–C5；[spike-claude-f.md](../research/spike-claude-f.md)：無說明 0/3、CLAUDE.md 說明 3/3、訊息標頭單獨 3/3、兩者並用 3/3、`claude-opus-5` 2/2、Stop hook 排隊 3/3 無迴圈。
